# 07. Модель безопасности

## 7.1. Аутентификация

| Механизм | Реализация |
|---|---|
| Пароли | `scrypt` (N=16384, r=8, p=1), 16-байтная соль, формат `scrypt$N$r$p$salt$hash`, сравнение `timingSafeEqual` |
| Access token | JWT HS256, TTL 15 минут, payload: `sub`, `companyId`, `role`, `type: "access"` |
| Refresh token | 48 случайных байт, в БД хранится SHA-256-хэш, TTL 30 дней, ротация при каждом обмене |
| Отзыв | `Session.revokedAt`; logout отзывает конкретную сессию |
| Повторное использование refresh | Использованный токен удаляется; попытка повторного использования не проходит (хэша нет) |

Секреты access и refresh — **разные** (`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`),
чтобы токен одного типа нельзя было предъявить как другой. Дополнительно в
payload есть поле `type`, которое проверяется.

## 7.2. Авторизация

Три роли:

| Роль | Права |
|---|---|
| `OWNER` | Всё, включая удаление сотрудников и компанию |
| `ADMIN` | Каталог, база знаний, AI-настройки, каналы, сотрудники (кроме удаления) |
| `MANAGER` | Лиды, диалоги, чтение каталога |

Проверка — middleware `requireRole(...roles)`. Правила целостности:
нельзя удалить/деактивировать последнего `OWNER`; нельзя понизить свою роль;
`MANAGER` не изменяет чужие сущности вне лидов и диалогов.

## 7.3. Изоляция арендаторов — три рубежа

1. **Источник `companyId`.** Берётся из JWT (`req.auth.companyId`) или, для
   вебхука, из `Channel`. Никогда — из тела запроса или query. Поле `companyId`
   в пользовательском вводе игнорируется схемами Zod (`.strip()`).
2. **Репозитории.** Каждый метод принимает `companyId` первым аргументом и
   включает его в `where`. Обновление и удаление выполняются через
   `updateMany`/`deleteMany` с `{ id, companyId }`, чтобы чужой `id` дал 0 строк,
   а не изменение чужой записи.
3. **Prisma guard-extension.** Расширение перехватывает все операции и бросает
   `TenantScopeError`, если для модели арендатора в `where`/`data` нет
   `companyId`. Это страховка от человеческой ошибки в новом коде.

### Два исключения, где арендатор ещё не известен

Guard применяется к клиенту `getPrisma()`. Клиент без расширения
(`getTenantResolutionPrisma()`) используется ровно в двух запросах, которые сами
и определяют арендатора:

| Запрос | Зачем | Почему это безопасно |
|---|---|---|
| `user.findUnique({ where: { email } })` | вход в систему | email уникален глобально; строка принадлежит одной компании, из неё и берётся `companyId` |
| `channel.findUnique({ where: { id } })` | приём вебхука Telegram | `channelId` приходит в URL, секрет вебхука сверяется constant-time; компания определяется найденным каналом |

Плюс `company.create` при регистрации — создание самого арендатора.
Любое другое обращение к незащищённому клиенту считается дефектом и должно
отклоняться на ревью.

Тесты `tests/unit/tenant-guard.test.ts` и `tests/integration/tenant-isolation.test.ts`
проверяют, что компания A не может прочитать или изменить данные компании B.

## 7.4. Секреты каналов

Токен Telegram-бота даёт полный доступ к переписке клиентов, поэтому:

- хранится зашифрованным: AES-256-GCM, ключ `ENCRYPTION_KEY` (32 байта hex),
  формат `v1:<iv-base64>:<tag-base64>:<ciphertext-base64>`;
- расшифровывается только в момент вызова Telegram API;
- в API-ответах маскируется (`1234567890:AAE***`);
- в логах не появляется: логгер имеет redact-список.

`webhookSecret` сравнивается constant-time; при ротации токена генерируется заново.

## 7.5. Валидация ввода

Zod на каждой границе: `body`, `query`, `params`, аргументы AI-инструментов,
CSV-импорт, апдейты Telegram. Правила:

- строки ограничены длиной (имя ≤ 200, описание ≤ 4000, сообщение ≤ 4096);
- числа — диапазонами (цена 0..10^12, лимит 1..100);
- телефон нормализуется к `+998XXXXXXXXX`, невалидный отклоняется;
- неизвестные поля отбрасываются (`.strict()` там, где это безопасно).

## 7.6. Лимиты запросов

| Маршрут | Лимит |
|---|---|
| `/auth/login`, `/auth/register` | 10 запросов / 15 минут / IP |
| `/webhooks/telegram/*` | 120 запросов / минуту / IP |
| Остальной API | 300 запросов / минуту / IP |
| AI-вызовы | не более 1 одновременного ответа на диалог (lock в памяти) |

## 7.7. Транспорт и заголовки

`helmet` (CSP, `X-Content-Type-Options`, `Referrer-Policy`, HSTS в проде),
CORS c явным списком origin из `WEB_ORIGIN`, `credentials: false`
(токен передаётся заголовком, не cookie), `express.json({ limit: "1mb" })`,
CSV-импорт `limit: 5mb`.

Nginx терминирует TLS, ставит HSTS и проксирует только `/api` на Node.

## 7.8. Логирование

`pino` с redact для `req.headers.authorization`, `botToken`, `password`,
`refreshToken`, `ENCRYPTION_KEY`. Каждый запрос получает `requestId`
(заголовок `X-Request-Id` или сгенерированный), который возвращается в теле
ошибки — по нему находится трассировка. Тела сообщений клиентов не логируются
на уровне `info`.

## 7.9. Что не отдаётся наружу никогда

`passwordHash`, `refreshTokenHash`, `botTokenCiphertext`, `webhookSecret`,
стектрейсы в проде, внутренние сообщения ошибок БД.

## 7.10. Чек-лист перед деплоем

- [ ] `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` ≥ 32 символов и различны
- [ ] `ENCRYPTION_KEY` — 64 hex-символа, сгенерирован случайно
- [ ] `NODE_ENV=production`
- [ ] `WEB_ORIGIN` указывает на реальный домен админки
- [ ] `PUBLIC_WEBHOOK_URL` — HTTPS с валидным сертификатом
- [ ] Порт Postgres не открыт наружу
- [ ] `npm run verify` зелёный
