# 09. Стратегия тестирования

## 9.1. Уровни

| Уровень | Инструмент | Что покрывает |
|---|---|---|
| Unit | Vitest | Чистая логика: скоринг лида, переходы статусов, определение языка, парсер CSV, парсер бюджета, scrypt/JWT/AES, guard мультиарендности, сборка промпта, форматирование карточек |
| Integration | Vitest + supertest | HTTP-контракты: авторизация, роли, валидация, конверт ответа, изоляция арендаторов, вебхук Telegram, полный путь «сообщение → лид» |
| Ручная приёмка | Чек-лист в `docs/08` | Сценарий владельца магазина в браузере |

## 9.2. Подход к базе данных в тестах

Интеграционные тесты работают против **фейкового хранилища** — реализации
интерфейсов репозиториев поверх структур в памяти (`tests/helpers/fake-store.ts`).
Это не мок с заглушками: фейк реально фильтрует, сортирует, применяет
`companyId`, соблюдает уникальные ключи и возвращает те же DTO, что и Prisma-слой.

Почему так:

- тесты запускаются на любой машине и в CI без Docker и без Postgres;
- прогон полного набора занимает секунды, поэтому его реально запускают;
- контракт репозитория один и тот же, поэтому подмена корректна.

Что при этом **не** покрыто и проверяется отдельно:

- SQL-специфика Prisma-запросов и индексы — проверяются при `db:migrate` и
  ручном прогоне на dev-БД;
- каскадные удаления — гарантируются схемой и проверяются на dev-БД.

Проверка на реальном Postgres выполняется отдельно и вручную перед релизом:
`npm run db:migrate && npm run db:seed`, затем прогон сценария владельца
магазина из `docs/08-roadmap-mvp.md`. Это единственная часть, которую
автоматические тесты не закрывают, и в отчёте о готовности она указывается явно.

## 9.3. Claude и Telegram в тестах

Оба внешних сервиса скрыты за интерфейсами:

- `ClaudeClient` → `FakeClaudeClient`, который отдаёт заранее заданную
  последовательность ответов, включая `tool_use`-блоки. Это позволяет проверить
  весь цикл tool-calling без сети и без затрат.
- `TelegramTransport` → `FakeTelegramTransport`, который записывает исходящие
  вызовы, чтобы тест утверждал: «отправлено 2 карточки товара и кнопка контакта».

## 9.4. Обязательные сценарии

1. Регистрация → вход → refresh → доступ к защищённому маршруту.
2. Компания A не читает и не изменяет данные компании B (products, leads,
   conversations, employees) — 404, а не 403, чтобы не раскрывать существование.
3. `MANAGER` не может изменить каталог.
4. CSV-импорт: валидные строки, битые строки, повтор по `external_id`.
5. Поиск товаров по цене и категории.
6. Полный путь Telegram: `update` → AI (fake) → ответ → карточки → контакт →
   `Lead.status = QUALIFIED`.
7. Вебхук с неверным секретом не создаёт ничего и отвечает `200`.
8. Переходы статусов лида, включая запрещённые.
9. Деградация AI при отсутствии ключа.

## 9.5. Порог покрытия

Порог задан в `vitest.config.ts` и проверяется командой `npm run test:coverage`:
строки, инструкции и функции — не ниже 80 %, ветвления — не ниже 70 %.

Фактическое состояние на момент завершения MVP:

| Метрика | Значение |
|---|---|
| Тестов | 195 (17 файлов) |
| Строки / инструкции | 93.1 % |
| Функции | 91.3 % |
| Ветвления | 80.4 % |

Из подсчёта исключены файлы без исполняемого кода (`**/types.ts`) и фабрика
`PrismaClient` (`core/prisma.ts`), которая проверяется миграциями и прогоном на
dev-базе, а не unit-тестами.
